你要的目标形态
-------

把原来的：

**多大 Agent 并排协作**

升级成：

**一个 Orchestrator Graph + 若干 Specialist Subgraph + 一套 Skill Registry**

也就是：

*   **顶层只保留一个总调度器**
*   Query / Media / Insight / Report 不再都是“重量级 Agent”，而变成**子图或工作流节点**
*   真正可复用的能力沉到 **Skill** 层
*   Forum 不再是“独立人格 Agent”，而是变成**评论/质检/补洞 skill 或 review subgraph**

这套思路和 LangGraph 的定位很契合。LangGraph 本身就是为 **long-running、stateful agent/workflow** 做编排的，而且官方把 **subgraph 作为 node** 明确支持，用来做多智能体系统、模块复用和分团队开发。[GitHub+1](https://github.com/langchain-ai/langgraph)

我建议你直接采用的升级版架构
--------------

### 1\. 顶层：Graph Orchestrator

用 **LangGraph** 做总编排最合适。原因不是它“最火”，而是它天然适合你这种“舆情分析是多阶段、长流程、会失败重试、需要状态共享”的系统。它官方强调的就是 **durable execution、human-in-the-loop、memory、stateful workflow**。[GitHub](https://github.com/langchain-ai/langgraph)

顶层图只做 6 件事：

*   `intent_parse`
*   `task_plan`
*   `dispatch_subgraphs`
*   `evidence_merge`
*   `review_or_reflect`
*   `report_finalize`

这样你会从“5 个互相聊天的大 agent”变成“1 个图控制 5 个业务分支”。

### 2\. 中层：业务子图，不是业务大脑

把 Veyrafish 现有五个引擎改造成四个真正的业务子图：

*   **Query Subgraph**
*   **Media Subgraph**
*   **Insight Subgraph**
*   **Report Subgraph**

ForumEngine 不建议继续保留成一个完整平级 Agent。更高效的做法是把它拆成两个能力：

*   `gap_finder_skill`：找证据缺口、找冲突
*   `critic/reviewer_subgraph`：做交叉审查、给补检索建议

LangGraph 的 subgraph 机制正适合这样做，因为它支持父图与子图之间定义清晰的状态接口，也支持子图作为节点被直接复用。[LangChain Docs](https://docs.langchain.com/oss/python/langgraph/use-subgraphs)

### 3\. 底层：Skill Registry

你说想利用上 skill，这个方向是对的，而且我建议你把 **skill 当成一等公民**，不要只把它理解成 prompt 模板。

我建议一个 skill 至少包含这 7 部分：

*   `name`
*   `input_schema`
*   `output_schema`
*   `instruction`
*   `tools`
*   `guardrails`
*   `budget/cache policy`

这其实和 Semantic Kernel 的 **plugin** 思路很接近：plugin 是一组可暴露给 AI 的函数集合，函数需要语义描述，且很适合和依赖注入结合；它还支持从本地代码、OpenAPI、MCP Server 导入。你完全可以借这个思想，把 Veyrafish 的 skill 做成“可注册、可复用、可替换”的能力包。[Microsoft Learn](https://learn.microsoft.com/en-us/semantic-kernel/concepts/plugins/)

为什么这会比原始多 Agent 更高效
-------------------

因为你现在真正需要的不是更多自治人格，而是更短的执行链路。

更精简的 agent 架构一般会做三件事：

第一，**把协作变成显式调度**。  
不是让 Agent 自己无限对话，而是由图决定什么时候调用哪个子图、什么时候结束。LangGraph 就是为这种显式图执行准备的。[GitHub+1](https://github.com/langchain-ai/langgraph)

第二，**把专家能力变成 tool / handoff / skill**。  
OpenAI Agents SDK 的思路就很典型：agent 由 instructions、tools、guardrails、handoffs 组成，handoff 还是通过工具语义来表示 delegation。这个模式非常适合把“专家 Agent”收缩成“轻量可委派节点”。[GitHub+1](https://github.com/openai/openai-agents-python)

第三，**把输出做成类型化**。  
PydanticAI 这类框架更强调 durable execution 和结构化输出校验。对舆情系统来说，这比“智能体人格感”重要得多，因为你的结果最终要进报告、进数据库、进可视化。[GitHub](https://github.com/pydantic/pydantic-ai)

你应该选哪套开源架构
----------

我给你一个很直接的结论：

### 最推荐：LangGraph + 自己的 Skill Registry

这是最适合 Veyrafish 的主架构。

原因是：

*   你本来就是 Python 项目
*   你本来就是多阶段长流程
*   你需要共享状态，而不是纯消息传递
*   你要的是“升级原架构”，不是推倒重做

LangGraph 负责 **流程编排**，Skill Registry 负责 **能力复用**，这套最稳。[GitHub+1](https://github.com/langchain-ai/langgraph)

### 补强层：PydanticAI 的输出约束思路

不一定要全框架切过去，但它的“durable + structured output validation”思路非常值得吸收。最起码你应该把所有 skill 输入输出都做成类型模型。[GitHub](https://github.com/pydantic/pydantic-ai)

### 轻量 handoff 层：OpenAI Agents SDK 的 delegation 思路

如果你有一部分节点仍想保留成“专家 agent”，那就用它的 **handoff** 思想：只有在需要的时候才把任务转给别的 agent，而不是一开始就让所有 agent 都上场。[GitHub+1](https://github.com/openai/openai-agents-python)

### Skill 设计参考：Semantic Kernel plugin

如果你想把 skill 做成标准化能力包，最值得参考的是 Semantic Kernel 的 plugin 思路，而不是传统 prompt library。它强调“函数组 + 语义描述 + DI + OpenAPI/MCP 接入”，非常适合企业系统。[Microsoft Learn](https://learn.microsoft.com/en-us/semantic-kernel/concepts/plugins/)

Skill 在你的系统里应该怎么用
-----------------

我建议你不要让 skill 只是“可调用函数”，而要让它承担这四个职责：

### 1\. 能力封装

比如 `stance_skill`，无论 Query/Media/Insight 谁要用，都走同一套输入输出。

### 2\. 执行策略

比如：

*   小任务走轻模型
*   高风险总结走强模型
*   重复任务命中缓存
*   超预算就降级

### 3\. 质量控制

配上 guardrails。OpenAI Agents SDK 官方就把 guardrails 放在一等位置，虽然它区分了 function tool guardrail 和 handoff pipeline，但这个设计思路很值得借。[GitHub+1](https://github.com/openai/openai-agents-python)

### 4\. 复用与组合

一个 subgraph 不是写死流程，而是动态组合 skill。

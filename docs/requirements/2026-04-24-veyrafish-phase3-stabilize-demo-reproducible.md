# Phase 3 需求文档：稳定、可演示、可复现

**状态**：已冻结  
**日期**：2026-04-24  
**运行模式**：`$vibe` interactive_governed  
**基于**：Phase 2.5 当前实现状态、前端规划文档、Skill 开发指南、当前测试基线

---

## 1. Goal

Phase 3 的目标不是继续追求更大的架构升级，而是把 Veyrafish 从“核心架构可跑、单测通过”推进到“稳定、可演示、可复现、可部署调试”的比赛交付状态。

本阶段围绕三轮主工作展开：

1. **前端界面重构轮**：继续按既有设计思路重构主界面，让系统能力更清晰、更适合演示。
2. **Skill 完善应用轮**：挑选对口、质量较高的 Skill，进一步接入主链路或调试链路，让 Skill 成为可解释的能力层。
3. **系统稳定轮**：补齐启动自检、端到端验收、真实配置联调、错误降级和回放基线。

Phase 3 结束后进入 Docker 部署调试阶段；Docker 可用后，再集中写操作文档、技术文档、部署文档和演示文档。

## 2. Deliverables

| 编号 | 交付物 | 说明 |
|------|--------|------|
| D1 | Phase 3 需求冻结与执行计划 | 明确三轮范围、顺序、门禁与回滚规则 |
| D2 | 前端重构第一批落地 | 保留现有功能，重构首页信息架构、系统控制区、任务进度与结果呈现 |
| D3 | Skill 应用增强 | 梳理已有 Skill 状态，选择对口 Skill 接入主流程、调试接口或报告上下文 |
| D4 | 稳定性治理 | 启动自检、依赖检查、配置检查、端到端验收脚本、日志与错误提示收口 |
| D5 | Docker 调试准备清单 | Docker 前置条件、环境变量、端口、数据目录、验收命令 |
| D6 | 文档写作输入材料 | 操作文档、技术文档、部署文档、演示脚本所需的真实步骤与截图清单 |

## 3. Constraints

- 不在 Phase 3 引入新的大调度框架，例如 LangGraph 替换、Celery 强绑定、微服务拆分。
- 不推倒现有 Flask + Streamlit 子进程运行方式，优先让当前架构稳定可演示。
- 前端重构必须保留当前核心 API 和功能入口，避免只做视觉替换导致功能回退。
- Skill 完善必须遵守 `docs/SKILL_DEVELOPMENT_GUIDE.md` 的 contract：schema、决策规则、禁止事项、降级策略、测试。
- 稳定性轮必须以真实启动、真实页面、真实 LLM 或明确 mock 回放为验收依据。
- Docker 调试放在 Phase 3 之后，不把 Docker 问题混入前端和 Skill 迭代主线。
- 文档写作放在 Docker 调通之后，避免提前写出和真实部署不一致的说明。

## 4. Acceptance Criteria

### 4.1 前端重构验收

- 首页第一屏能清楚表达系统状态、任务入口、运行进度和关键结果。
- 系统控制、LLM 配置、引擎状态、Forum、报告输出的职责边界比当前单页壳更清晰。
- 原有启动、搜索、任务查询、报告查看、日志查看能力不退化。
- 前端改动经过浏览器手动检查，移动端和桌面端无明显文本重叠或关键按钮不可见。

### 4.2 Skill 应用验收

- 已登记当前 7 个内置 Skill 的状态：已主链路接入、可扩展接入、备用能力、暂缓能力。
- 至少完成一批高价值 Skill 应用增强，不追求数量，优先追求对主链路有真实帮助。
- 新增或调整的 Skill 必须有单元测试或集成测试覆盖。
- 外部服务、LLM、解析失败时必须有稳定降级路径。

### 4.3 系统稳定验收

- `python -m pytest` 全量通过，新增测试不引入回归。
- 存在最小启动自检，能检查依赖、环境变量、端口、关键目录、API Key 状态。
- 能完成至少一次本地端到端演示流程：启动主页、提交任务、观察三引擎/Forum、生成或查看报告。
- 端到端流程失败时有明确错误信息，不让用户只看到静默失败。

### 4.4 Docker 前置验收

- Phase 3 结束时输出 Docker 调试准备清单。
- 明确 Docker 需要的 `.env` 字段、端口、数据挂载目录、启动命令和验收 URL。
- 明确哪些问题进入 Docker 阶段解决，哪些问题必须在 Docker 前先解决。

## 5. Product Acceptance Criteria

- 比赛演示者能在 5 分钟内说明系统当前能力、启动方式、一次任务流程和报告产出路径。
- 系统出现配置缺失时，前端或日志能给出可理解提示。
- 评委视角下，界面不再像开发控制台堆叠，而像一个有明确流程的舆情分析系统。
- 技术答辩时，可以讲清楚 Skill、Evidence、Graph、TaskStore 在系统中的位置和价值。

## 6. Manual Spot Checks

- 打开首页，检查是否能快速找到“启动系统”和“发起分析”的主路径。
- 检查前端是否仍有系统运维按钮和产品操作按钮混杂的问题。
- 运行固定样例任务，检查任务状态、日志、Forum、报告产出是否可追踪。
- 手动断开或缺失一个 API Key，检查错误提示是否可理解。
- 检查 Skill 输出是否有结构化字段，而不是只返回散文式文本。

## 7. Completion Language Policy

- 只完成代码改造时，表述为：`代码主路径完成，待真实链路验收`。
- 通过单测但未浏览器验收时，表述为：`测试门禁通过，产品验收未完成`。
- 完成一轮真实端到端演示后，才允许表述为：`本地演示链路通过`。
- Docker 未调通前，不允许表述为：`可部署`。
- 文档未与真实步骤核对前，不允许表述为：`文档完成`。

## 8. Delivery Truth Contract

本阶段结论以以下证据为准：

- 代码测试结果。
- 浏览器手动检查结果。
- 真实或固定回放任务输出。
- 启动自检结果。
- Docker 调试记录。
- 文档中的命令能在当前项目中复现。

## 9. Non-goals

- 不做前后端完全分离。
- 不做微服务拆分。
- 不做完整插件市场。
- 不在 Phase 3 内完成最终操作手册和技术白皮书。
- 不把 Docker 部署调试提前混入三轮核心建设。

## 10. Autonomy Mode

默认采用串行治理模式：

- 每一轮先冻结本轮目标，再实施，再验收。
- 前端轮和 Skill 轮可以在局部任务上并行分析，但实际合并按串行门禁推进。
- 稳定轮必须在前两轮之后作为收口，不提前宣布阶段完成。

## 11. Inferred Assumptions

- Phase 2.5 当前核心测试已经通过，Phase 3 可以以稳定和演示为主。
- 当前 `templates/index.html` 仍承担过多职责，前端轮需要先做信息架构收敛。
- 当前 Skill 已有 7 个内置实现，Phase 3 重点是“选择性应用”，不是盲目增加数量。
- Docker 调试会暴露环境依赖、端口和路径问题，因此应在本地稳定后再进入。
- 文档必须基于真实调试结果编写，否则后期会产生大量偏差。

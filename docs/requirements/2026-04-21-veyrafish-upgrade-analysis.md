# Veyrafish 升级分析需求冻结

日期：2026-04-21
运行模式：`/vibe`
主题：为 Veyrafish 梳理下一阶段可落地的升级点、架构方向与实施优先级

## 1. Goal

基于现有仓库、已有分析文档与关键代码路径，输出一份面向二次开发的升级分析，明确：

- 这个项目当前最值得投入的升级点是什么
- 哪些“现代但成熟”的技术或架构适合引入
- 哪些改动应当先做，哪些不应过早做
- 如何把升级拆成能逐步落地的路线图

## 2. Deliverable

本次交付物包括：

- 一份升级方向主文档：`UPGRADE_DIRECTIONS.md`
- 一份需求冻结文档：本文
- 一份执行计划：`docs/plans/2026-04-21-veyrafish-upgrade-analysis-execution-plan.md`
- 一组运行治理记录：`outputs/runtime/vibe-sessions/20260421-veyrafish-upgrade-analysis/`

## 3. Constraints

- 以当前仓库真实实现为准，不能只复述已有文档
- 不空谈“上微服务”“上 AI 平台”，建议必须能映射到当前代码结构
- 优先推荐成熟、当前仍然活跃的技术方案
- 保持渐进式升级思路，避免默认推翻重写
- 当前环境不是可用 Git 工作树，不能依赖分支/提交历史判断演进脉络
- 当前本地 Python 环境缺少测试依赖，测试结论需要区分“未覆盖”与“无法执行”

## 4. Acceptance Criteria

- 明确指出 Veyrafish 当前的核心架构优点与真实瓶颈
- 给出至少 3 个层级的升级方向：基础治理、架构升级、产品化增强
- 给出推荐主路线，并说明为什么不是微服务优先
- 给出 30/60/90 天或分阶段路线图
- 对关键推荐技术给出适用边界，而不是简单罗列技术名词
- 所有关键判断都能回溯到仓库文件或官方资料

## 5. Product Acceptance Criteria

- 文档能直接作为后续拆任务、写 issue、做技术评审的输入
- 结论能帮助决定“下一步先改什么”，而不是仅提供概念说明
- 同时覆盖研发效率、系统稳定性、Agent 质量、部署维护成本

## 6. Manual Spot Checks

- 检查主编排层是否依赖 Flask + Streamlit 子进程
- 检查 Agent 间通信是否依赖日志文件与 Markdown 文件
- 检查配置是否存在根配置与子模块配置重复定义
- 检查测试是否形成有效回归保护
- 检查 ReportEngine 是否已经具备可保留和可继续投资的中间层能力

## 7. Completion Language Policy

- 只有在完成仓库抽样核查、形成优先级和落地路线后，才允许使用“已完成分析”
- 不能把“未来可考虑”表述成“当前应当实施”
- 若测试未执行成功，必须明确写明原因

## 8. Delivery Truth Contract

- 仓库内证据来自 `README.md`、`DEVELOPMENT.md`、`MODULE_ANALYSIS.md` 与关键实现文件
- 外部技术建议仅参考官方文档或官方稳定文档站点
- 任何对项目现状的判断，都应优先来自本地代码而非 README 宣传描述

## 9. Non-goals

- 本次不直接改造业务代码
- 本次不直接迁移前后端框架
- 本次不直接替换 LLM 供应商
- 本次不直接重构为微服务

## 10. Autonomy Mode

默认自主推进；在不需要用户补充上下文的前提下，直接完成分析、分级和文档落盘。

## 11. Inferred Assumptions

- 用户当前目标是“确定升级方向”，不是“立刻改完整架构”
- 用户愿意保留现有多 Agent 产品形态，而非把项目改造成完全不同的产品
- 现阶段更关注可维护性、可扩展性、可部署性，而不是单点极致性能
- ReportEngine 的 IR 能力和模块边界值得继续投资，不应轻易推翻
